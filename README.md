# Sumo Top View — AprilTag + ESP32

ใช้คอมพิวเตอร์อ่านกล้องเหนือสนามและวางแผนต่อเนื่อง **เลือก ID หุ่นเราและศัตรูจากแท็กที่กล้องเห็น**
ไม่จำกัดว่าต้องใช้ ID 1/2 แล้วส่งค่าล้อซ้าย/ขวาไปยัง ESP32 ผ่าน **Wi-Fi UDP เท่านั้น**
มีหน้าจอแสดงภาพกล้อง ทิศหัวหุ่น แผนการเดิน ทางที่เดินจริง ปุ่ม **Start / Stop**
และโหมดจำลองที่ทดลองได้โดยไม่ต้องต่อหุ่น ไม่แก้ไขหรือใช้ไฟล์ในโฟลเดอร์ `test`

ค่าตั้งต้นตามสนามจริง: **84 × 84 cm รวมขอบขาว**, ขอบขาวด้านละ **5 cm**
จึงเหลือพื้นที่สีดำ **74 × 74 cm** หุ่นเราและศัตรู **กว้าง 18 × ยาว 21 cm เท่ากัน**
ระบบใช้ตัวหุ่นสี่เหลี่ยมที่หมุนตามทิศหัว ทั้งในการหลบและตรวจระยะจากขอบสนาม

## เริ่มใช้

เครื่องนี้ติดตั้ง dependency และโปรไฟล์ฮอตสปอต Wi-Fi ให้แล้ว เปิด **Sumo Top View** บน Desktop
หรือไฟล์ **`Sumo Top View.lnk`** ในโปรเจกต์เพียงไฟล์เดียวเพื่อใช้งานได้
ตัวเปิดนี้อ้างอิง Python ใน `.venv` ของโปรเจกต์ จึงต้องเก็บโฟลเดอร์โปรเจกต์ไว้ตำแหน่งเดิม
ไฟล์ `run_topview.bat` ยังเปิดใช้งานและใช้ดูข้อความผิดพลาดได้ตามเดิม

การเชื่อมต่อใช้ **ฮอตสปอตเดิมชื่อ Kittifirst**: ทั้งคอมและ ESP32 เป็นลูกข่ายของฮอตสปอตเดียวกัน
ESP32 ไม่สร้างเครือข่าย Kittifirst ขึ้นมาเอง และ IP ของหุ่นขึ้นกับ DHCP ของฮอตสปอต

หลังอัปโหลด ESP32 สำเร็จแล้ว เปิดไฟหุ่น จากนั้นเปิดโปรแกรม:

1. เปิดฮอตสปอต **Kittifirst** ที่รองรับ 2.4 GHz ให้คอมต่อเครือข่ายนี้
   ESP32 จะใช้ชื่อและรหัสใน `src/main.cpp` เพื่อเข้าฮอตสปอตด้วย
   โปรแกรมช่วยขอเชื่อมฮอตสปอตให้คอมเมื่อพบเครือข่ายนี้ได้
   ถ้ายังไม่พบ ให้เปิดฮอตสปอตแล้วกด **เชื่อมต่อ Wi-Fi หุ่น** อีกครั้ง
2. รอป้าย **Wi-Fi • เชื่อมต่อแล้ว** สีเขียว ซึ่งหมายถึง ESP32 ตอบ `PING/PONG` จริง
   ช่อง IP ใช้ `auto` เพื่อค้นหา IP ของหุ่นจากคำตอบในเครือข่ายเดียวกัน ไม่ยึด `192.168.4.1`
   แสดง IP ที่พบ, port, RTT และเวลาตอบกลับล่าสุด ป้ายเปลี่ยนเป็นสีแดงเมื่อขาดการตอบกลับ
3. เลือกกล้องและเปิดภาพ เลือก ID ในช่อง **หุ่นเรา**
   ถ้าเห็นอีกหนึ่ง ID จะเลือกศัตรูให้ ถ้ามีหลาย ID ให้เลือกศัตรูเอง
4. กำหนดมุมสนามครั้งแรก ตรวจลูกศร FRONT และแผนเส้นเหลือง แล้วกด **Start**

เปิดโปรแกรมหรือเชื่อม Wi-Fi อย่างเดียวไม่ทำให้หุ่นเดิน ต้องกด Start เสมอ
เลือก ID ใหม่ได้ขณะหยุด และจำค่าที่เลือกเมื่อบันทึก/เริ่มใช้งาน

สำหรับติดตั้งบนเครื่องอื่น:

ใช้ Python 3.10 ขึ้นไป ติดตั้ง dependency ใน environment ของโปรเจกต์:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\run_topview.bat --demo
```

หากยังไม่มี `.venv`:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

กด **Start** ในโหมดจำลองเพื่อดูการเข้าข้าง เลือกพฤติกรรมศัตรูในแท็บ **จำลอง**
หรือกด **จำลองชนค้างหน้าชนหน้า** ก่อน Start เพื่อดูการถอยและเปลี่ยนฝั่ง
แบบจำลองนี้ใช้ตรวจพฤติกรรมและการควบคุม ไม่ได้ทำนายแรงชน แรงเสียดทาน หรือผลการแข่งขันจริง

เปิดโปรแกรมใช้งานจริงด้วย `run_topview.bat` หรือ:

```powershell
.\.venv\Scripts\python.exe topview_controller.py
```

## เตรียมกล้องและสนามจริง

1. ติดกล้องเหนือสนามให้ตั้งฉากมากที่สุด ภาพต้องไม่ mirror และเห็นขอบสนามครบตลอดเวลา
   ยึดกล้องและล็อกการซูม เลือกความละเอียด/แสงให้แท็กทั้งสองอ่านได้เมื่อหุ่นหมุน
   โปรแกรมขอภาพ 1280×720 แต่ backend อาจเลือกขนาดอื่น
2. ติดแท็กไว้กึ่งกลางหุ่นทั้งสองตัว ใช้ family เดียวกัน: `36h11` เป็นค่าเริ่มต้น
   หรือเลือก `36h10` ให้ตรงแท็กจริง ติดให้ราบและเห็นได้จากกล้อง
3. ปิดโหมดจำลอง กด **ค้นหากล้องใหม่** เลือกกล้องตามชื่อ แล้วกด **เปิดภาพกล้อง**
   บน Windows มีทั้ง DSHOW และ MSMF รวมถึงกล้องเสมือน Camo
   หากเปิดรายการหนึ่งไม่ได้ให้ลอง backend อีกตัว และปิดโปรแกรมอื่นที่ใช้กล้อง
   เมื่อเห็นแท็ก เลือก ID ในช่อง **หุ่นเรา** และ **ศัตรู** ให้ตรงกับหุ่นจริง
4. ตั้งค่าขนาดสนาม ขอบขาว ขนาดหุ่น และค่าล้อในแท็บ **ขนาด / มอเตอร์** แล้วกด **ใช้ค่า / บันทึกค่า**
   ค่าเริ่มต้นสนาม **840 × 840 mm** ขอบขาวด้านละ **50 mm** หุ่นทั้งสอง **180 × 210 mm**
   กว้างหมายถึงซ้ายถึงขวาของหุ่น ยาวหมายถึงหน้าถึงหลัง รวมใบดันและส่วนยื่นทั้งหมด
5. กด **กำหนดมุมนอก** แล้วคลิก **มุมสนามด้านนอกสุดที่รวมขอบขาว** ตามลำดับ:
   **ซ้ายบน TL → ขวาบน TR → ขวาล่าง BR → ซ้ายล่าง BL**
   ห้ามคลิกที่มุมพื้นที่สีดำ เพราะสเกลอ้างอิงขนาดรวม 840 mm
   Calibration แบบวงกลมของเวอร์ชันเดิมใช้ต่อไม่ได้ ต้องกำหนดมุมใหม่ครั้งหนึ่ง
6. ดูลูกศร **FRONT** ของทั้งสองหุ่นบนภาพและแผนที่ ปรับ **มุมหัวหุ่นเรา / ศัตรู**
   แยกกันจนลูกศรชี้ไปที่หน้าหุ่นจริง แล้วกดใช้ค่า
   ค่า 0° หมายถึงขอบบนของแท็กตามทิศที่ถอดรหัส; มุมบวกหมุนทวนเข็มนาฬิกาในสนาม
7. ย้ายหุ่นทดลองไปหลายตำแหน่ง ตรวจว่าตำแหน่ง ระยะ และลูกศรบนแผนที่ตรงกับสนามจริง
   ค่าถูกบันทึกใน `sumo_settings.json` แต่หากย้าย/ซูมกล้องหรือย้ายจุดติดแท็ก ต้องกำหนดสนามใหม่

การแปลงภาพใช้ planar homography หน่วย mm จึงสมมติว่าสนามราบ
ความสูงของแท็กจากพื้นและเลนส์มุมกว้างทำให้ตำแหน่งคลาดเคลื่อนได้
ติดกล้องให้สูงและตั้งฉาก ใช้แท็กที่ความสูงใกล้กัน และเพิ่มระยะเผื่อขอบตามความคลาดเคลื่อนที่วัดได้
ภาพที่ค้างอยู่ภายในมือถือ/virtual camera ตรวจไม่ได้จากเวลาอ่านของโปรแกรมเพียงอย่างเดียว
จึงต้องตรวจความหน่วงจริงของกล้องด้วย

## ต่อหุ่นและเริ่มทำงาน

Build / Upload `src/main.cpp` ด้วย environment **esp32dev**:

```powershell
pio run -e esp32dev
pio run -e esp32dev -t upload
```

ตั้งพอร์ตอัปโหลดเครื่องนี้เป็น `COM5` (CP210x) และความเร็ว `57600` เพื่อแยกตรวจอาการ Flash MD5 ไม่ตรง
หาก Windows เปลี่ยนหมายเลข COM ให้แก้ `upload_port` ใน `platformio.ini`
หากพบ `MD5 of file does not match data in flash` ให้ปิดไฟมอเตอร์และตัดไฟวงจรก่อนถอดสาย
ถอดสายสัญญาณ IR จาก GPIO12 ชั่วคราว แล้วต่อ ESP32 กับ USB อย่างเดียวเพื่อทดสอบอัปโหลด
ขา GPIO12 เป็นขา strapping ที่อาจเลือกแรงดัน Flash 1.8 V เมื่อถูกดึง HIGH ตอนรีเซ็ต
หากยังไม่ผ่าน ให้เปลี่ยนสาย USB และพอร์ต USB ที่ต่อตรงเข้าคอม แล้วอัปโหลดใหม่
อ้างอิง [Espressif: boot mode / GPIO12](https://docs.espressif.com/projects/esptool/en/latest/esp32/advanced-topics/boot-mode-selection.html#other-pins)
และ [Flash troubleshooting](https://docs.espressif.com/projects/esptool/en/latest/esp32/troubleshooting.html)

อัปโหลดไฟล์ล่าสุดให้ขึ้น `SUMO_TOPVIEW_WIFI_STA_V6_AUTO` เฟิร์มแวร์นี้ **เปิดเครื่องแล้วหยุด** รอ Start ครั้งเดียว
หลัง Start หุ่นเล่นต่อเองจนกด Stop หรือกล้องยืนยันผลชนะ/แพ้ ไม่ต้องเริ่มใหม่เมื่อภาพหรือ Wi-Fi หลุด
คืนพฤติกรรมเดิมจาก [ต้นแบบที่กู้จาก VS Code Local History](reference/original_state_machine.cpp.txt):
เดินค้นหาที่ 140, IR เจอแล้วเล็งเข้าชน 255, พื้นขาวให้ถอยและหันกลับ

**Wi-Fi แบบไม่ใช้สาย:** ESP32 ใช้โหมด **Station (STA)** เข้าเครือข่าย **Kittifirst** เช่นเดียวกับคอม
ใช้รหัสที่ตั้งไว้ใน `src/main.cpp` แล้วรับ IP จากฮอตสปอต อุปกรณ์นี้ใช้ UDP port `4210`
แอปส่ง PING เพื่อค้นหาหุ่น และยอมรับ IP จาก PONG ที่ตรงกับหมายเลขตรวจสอบรอบนั้นเท่านั้น
เมื่อพบแล้ว การควบคุมจะคุยเฉพาะ IP/port ที่ตรวจสอบแล้ว การค้นหาหุ่นอย่างเดียวไม่สั่งให้เดิน
ถ้า Windows ไม่อนุญาต ให้กด **เปิดการตั้งค่า Wi-Fi ของคอม** แล้วเลือกเครือข่ายนี้เอง
เมื่อไม่มีเครือข่าย Kittifirst จะไม่เปลี่ยนเครือข่ายเดิมของคอม
ตัวตรวจ PING/PONG ทำงานต่อเนื่องขณะหยุดด้วย ไม่เริ่มมอเตอร์หรือยืดอายุคำสั่งภาพ
เปลี่ยน SSID/รหัสผ่านได้ที่ต้น `src/main.cpp` และให้แก้ `robot_wifi.xml`, `sumo/wifi.py` ให้ตรงกันด้วย
หากใช้กล้องมือถือผ่าน Wi-Fi ให้ตรวจว่าแอปกล้องส่งภาพถึงคอมได้ขณะเปิดฮอตสปอตด้วย
กล้อง USB หรือ Camo ผ่าน USB ใช้ส่งภาพได้เช่นเดิม การควบคุมหุ่นยังคงใช้ Wi-Fi

ตรวจว่า ESP32 เชื่อมจริงตามลำดับนี้:

1. งานอัปโหลดต้องจบ `SUCCESS` หากยังมี MD5 error จะยังยืนยันไม่ได้ว่าเฟิร์มแวร์ใหม่ทำงาน
2. ดูรายชื่อ/จำนวนอุปกรณ์ในฮอตสปอต ควรมี ESP32 เพิ่มขึ้นหลังเปิดไฟหุ่น
3. เปิด Serial Monitor `COM5`, `115200` baud แล้วกด EN เพื่อดู log ตั้งแต่เริ่มบูต รวมสถานะ Wi-Fi และ IP ที่ ESP32 ได้รับ
   ถ้ายังค้างที่กำลังเชื่อม ให้ตรวจชื่อ รหัสผ่าน และฮอตสปอตที่รองรับ 2.4 GHz
4. คอมต้องต่อฮอตสปอตเดียวกัน แล้วรอ PING/PONG ในแอปให้ขึ้นสีเขียวพร้อม RTT
   ชื่อ Wi-Fi ตรงกันอย่างเดียวไม่ใช่หลักฐานว่าแอปคุยกับ ESP32 ได้

ใน Serial Monitor ควรเห็นทั้งสองบรรทัดนี้ โดย `IP=...` เป็นเลข IP ที่ได้รับจริง:

```text
WIFI CONNECTED SSID=Kittifirst HOST=sumo-robot IP=...
UDP READY IP=... PORT=4210
```

`WIFI CONNECTED` ยืนยันว่าหุ่นเข้าฮอตสปอตได้ ส่วน `UDP READY` ยืนยันว่าเปิดพอร์ตรอคำสั่งแล้ว
จากนั้น PONG สีเขียวในแอปจึงยืนยันการสื่อสารระหว่างคอมกับหุ่นอีกชั้นหนึ่ง

หากค้นหาอัตโนมัติไม่พบ แต่ ESP32 รายงานว่าเชื่อมต่อแล้ว ให้กรอก **IP ของ ESP32 ที่เห็นใน Serial Monitor**
แทน `auto` แล้วกดเชื่อมต่อใหม่ IP นี้ไม่ใช่ IP ของคอม และอาจเปลี่ยนหลังเปิดฮอตสปอตใหม่
`192.168.4.1` เป็นค่าโหมด AP ของเวอร์ชันเก่า จึงไม่ใช้เป็นค่าเริ่มต้นในโหมดฮอตสปอตร่วมกันนี้
หากกรอก IP ตรงแล้วยังไม่ตอบ ให้ตรวจว่าฮอตสปอตอนุญาตให้อุปกรณ์ลูกข่ายสื่อสารถึงกัน

สาย USB ใช้สำหรับอัปโหลดเฟิร์มแวร์และดู log การควบคุมเดินหุ่นจากโปรแกรมใช้ Wi-Fi
Serial Monitor 115200 baud ยังใช้ดู log และส่ง `s` เพื่อหยุดได้ แต่ ARM/DRIVE ไม่รับทาง Serial

เมื่อเห็นแท็กทั้งสอง สนามกำหนดแล้ว และหุ่นเราอยู่ในเส้นปลอดภัย กด **Start**
โปรแกรมรอ ESP32 ยืนยัน ARM ก่อนส่งคำสั่งล้อ จากนั้นวางแผนซ้ำจากภาพล่าสุด
เป้าหมายรอบควบคุมอยู่ที่ **20 Hz** โดยขึ้นกับความเร็วกล้องและเครื่อง

กด **Stop**, **Esc** หรือปิดหน้าต่างเพื่อหยุด ต้องกด Start ใหม่จึงเริ่มอีกครั้ง
แท็กหาย/ซ้ำ ภาพเก่า กล้องเสีย หรือ Wi-Fi ขาด ให้ ESP32 ใช้ state เดินหา/IR/หลบขอบต่อเอง
พอเห็นสองแท็กในภาพใหม่ที่ใช้ได้ กล้องกลับมาวางแผนเข้าโค้งเองทันที ไม่ต้อง Start ซ้ำ
ยืนยันชนะ/แพ้เมื่อแท็กอยู่นอกสนามต่อเนื่องอย่างน้อย 0.35 วินาทีและเห็นอย่างน้อย 3 ภาพใหม่
ไม่ตีความแท็กหายว่าเป็นชัยชนะ ถ้าไม่เห็นให้เดินค้นหาต่อ
ถ้า Stop ขณะเครือข่ายขาด แอปเก็บคำสั่งและส่งซ้ำเมื่อเชื่อมได้ จะแสดง **STOP • รอยืนยัน**
หากต้องหยุดทันทีขณะติดต่อหุ่นไม่ได้ ให้กด EN/รีเซ็ตบน ESP32 ซึ่งบูตกลับมาที่ STOP

## ระบบพิจารณาการเข้าชนอย่างไร

- หา center และทิศหัวจากมุมแท็ก แล้วแปลงเข้าพิกัดสนาม: +x ขวา, +y ขึ้น, มุมบวกทวนเข็มนาฬิกา
- ประเมินความเร็วศัตรูจากภาพ คาดตำแหน่งล่วงหน้า 0.22 วินาที โดยจำกัดระยะคาดการณ์ 70 mm
- ช่วงเปิดเกมพยายามเข้าโค้งด้านข้างก่อน เลือกได้ทั้งหน้าข้าง ข้าง และหลังตามพื้นที่จริง
  จุดหลังศัตรูที่อยู่นอกสนามจะไม่ถูกเลือก ไม่บังคับอ้อมไปจุดนั้น
  ให้คะแนนจากระยะทาง มุมที่ต้องหมุน โอกาสดันออกขอบ และค่าป้องกันการสลับฝั่งถี่เกินไป
- ใช้ A* หาแนวช่องเดิน แล้วเลือกคำสั่งล้อจริงจากเส้นโค้งของ differential drive
  ตรวจตำแหน่งและมุมตัวหุ่นสี่เหลี่ยมตลอดโค้ง รวมระยะเผื่อระหว่างตัวอย่าง
  เลือกเดินพร้อมเลี้ยวเป็นหลัก หมุนอยู่กับที่เฉพาะเมื่อเป้าหมายอยู่หลังหรือไม่มีช่องให้โค้ง
  ประเมินคำสั่งใหม่ทุก 50 ms และปรับเส้นทางเมื่อศัตรูเคลื่อนหรือหัน
- ถึงระยะเข้าชนแล้วใช้ `INTERCEPT` / `PUSH` ต่อทันที ไม่รอให้ถึง waypoint แบบเป๊ะ ๆ
  ถ้าอ้อมไม่ได้หรือหน้าชนกันอยู่แล้ว ให้ `ATTACK_FRONT` ดันตามจังหวะที่เข้าถึงได้
  การเข้าชนจงใจยอมให้สัมผัสศัตรู แต่ยังตรวจตัวหุ่นเรากับขอบสนาม
- IR ทั้ง 5 ตัวอ่านบน ESP32 ต่อเนื่อง: กลางเจอให้ดัน, หน้าซ้าย/ขวาเจอให้โค้งเข้าหา,
  ซ้าย/ขวาสุดเจอให้เลี้ยววงแคบเข้าจับ แสดง `IR_PUSH`, `IR_LEFT`, `IR_SIDE_RIGHT` ฯลฯ
  คอมใช้ IR ช่วยเลือกเข้าชนด้วย ไม่ใช่แสดงค่าอย่างเดียว
- โหมดภาพให้ IR เสริมเข้าชนตลอดช่วงเดิน/เข้าโค้ง ไม่ปิด IR เพราะระยะเผื่อจากกล้อง
  คำสั่งภาพมีอายุ 350 ms เพื่อทนความหน่วง Wi-Fi เซนเซอร์พื้นมีสิทธิ์หลบขอบก่อน IR เสมอ
  IR ไม่แทรกคำสั่งถอยหรือหยุด
- ถ้าศัตรูยังขยับไปข้างหน้าหรือเข้าใกล้ขอบ ให้ดันต่อ แม้ระยะขยับยังน้อยกว่าเกณฑ์ชนค้างเดิม
  ถอยเฉพาะเมื่อยืนยันว่าไม่คืบหน้าอย่างน้อย **2 วินาที**; ใกล้ขอบให้เวลาปิดเกมอย่างน้อย **3.2 วินาที**
  แล้วค่อยถอยสั้นประมาณ **85 mm** ไม่เกิน **0.7 วินาที**
  แล้วเพิ่มความต้องการเข้าจากอีกฝั่ง ก่อนคำนวณใหม่ตามภาพจริง
  เว้นการถอยซ้ำอย่างน้อย 4 วินาที หรือ 6 วินาทีเมื่อศัตรูใกล้ตก ป้องกันวนถอย-ชนซ้ำถี่ ๆ
- หากใกล้ขอบเกินระยะเผื่อ ให้กลับเข้าพื้นที่สีดำ (`EDGE_RETURN`)
  หากไม่มีช่องเข้าข้าง ให้เข้าจากด้านที่เข้าถึงได้ ถ้าพื้นที่เลี้ยวแคบให้เปิดระยะเข้ากลางสนาม
  ถ้าหาโค้งภาพไม่ได้ ให้กลับไป state บนหุ่น ไม่ส่งค้างที่ `CLEARANCE_HOLD`

เส้นเหลืองแสดงแนวเข้าโค้งตั้งแต่หุ่นเราผ่านจุดอ้อมจนถึงเป้าบนศัตรู ปรับตามตำแหน่งล่าสุด
เห็นเส้นแผนล่วงหน้าในโหมด PREVIEW ก่อน Start ได้แม้หุ่นอยู่นิ่ง ใช้เส้นทึบทั้งก่อนเริ่มและขณะวิ่ง
ส่วนหลังจุดสัมผัสเป็นทิศเล็งดัน ไม่ได้หมายความว่าศูนย์กลางหุ่นเราจะไปทับแท็กศัตรู
เส้นฟ้าแสดงโค้งจากคำสั่งล้อเฉพาะรอบนี้ เส้นเขียวแสดงตำแหน่งที่อ่านได้จริง
เส้นวิ่งจริงแสดงสีเขียวสว่างทั้งบนภาพกล้องและแผนที่ บันทึกจากตำแหน่งแท็กเราแม้ศัตรูหายหรือใช้โหมด IR
กด **รีเซ็ตเส้น / เวลา** ด้านบนภาพเพื่อล้างเส้นเก่าและเริ่มเวลาใหม่ระหว่าง AUTO ได้ หุ่นทำงานต่อ
ช่อง **แสดงเส้นวิ่งจริง** ใช้ซ่อน/แสดงเส้นเก่า ตัวจับเวลาเริ่มเมื่อ Start และค้างไว้เมื่อ Stop
Start รอบใหม่ล้างเส้น/เวลาให้เอง หากแท็กหายหรือตำแหน่งกระโดดจะเว้นช่วงเส้น ไม่ลากข้ามสนาม
เส้นทางอ้อมจะลดความโค้งเมื่อมีพื้นที่แคบ แทนการวาดเส้นลัดผ่านศัตรูหรือขอบ

ท้ายหุ่นทับขอบขาวได้หากตัวยังอยู่บนสนาม ไม่ถือว่าผิดเขตหรือสั่งถอยเพราะท้ายแตะขาวอย่างเดียว
`FRONT → WHITE` คือระยะหน้าหุ่นถึงขอบขาว และ `BODY → OUTER` คือระยะตัวหุ่นถึงขอบตกจริง
เส้นประแสดงขอบเขตศูนย์กลางแบบไม่สมมาตรตามมุมหุ่น: ด้านหน้าเผื่อสีดำ 25 mm ขณะที่ท้ายใช้ขอบขาวได้
แผนจากภาพตรวจโค้งตามขอบนอกโดยเผื่อ 4 mm และระยะระหว่างตัวอย่าง
ค่านี้ไม่ใช่เงื่อนไขปฏิเสธ Start: ตัวเลข 3 mm ยังเริ่มได้ แล้วหุ่นกลับเข้าสนามเอง
ช่วงเข้าชนใช้การคาดการณ์สั้นให้สั่งเต็มกำลังได้ เซนเซอร์พื้นด้านหน้าบน ESP32 ยังสั่งถอยทันทีเมื่อพบขาว

ค่าล้อคำนวณจากความคลาดเคลื่อนมุมและระยะถึง waypoint ด้วย differential drive:

```text
curvature = 2 * sin(target_heading - robot_heading) / lookahead_distance
omega = v * curvature
v_left  = v - omega * wheel_base / 2
v_right = v + omega * wheel_base / 2
PWM ≈ v_wheel / max_wheel_speed * 255
```

เลือกเส้นโค้งที่เคลื่อนเข้าหาเป้าหมายและมีพื้นที่ให้ตัวหุ่นกวาดผ่าน ใช้ PWM ได้ทั้งบวก/ลบ
มีค่าชดเชยแต่ละล้อ ค่าขั้นต่ำให้มอเตอร์เริ่มหมุน และเพดานเริ่มต้น **255/255**
เข้าชน/IR จับวัตถุและถอยใช้กำลังเต็มตามเพดาน ส่วนการเดินอ้อมปรับอัตราส่วนล้อเพื่อเข้าโค้ง
คำสั่งถอยไม่คูณลดแรง 0.65/0.70 แบบเดิม และการหลบขอบบน ESP32 ใช้ 255 เช่นกัน
ค่าความเร็วเป็นค่าประมาณจากการสอบเทียบ ไม่มี encoder จึงต้องวัดความเร็วที่แบต/พื้นจริง
ระบบภาพจะปรับทิศและเป้าหมายซ้ำ แต่ไม่สามารถรับประกันผลชนะได้หากแรงดัน ความเร็ว หรือแรงยึดเกาะเสียเปรียบ

### แท็กหลุดและ Search บน ESP32

- `AUTO_SEARCH_FWD` เดินหน้าค้นหาที่ 140 ตามต้นแบบ สลับเดินโค้งกว้าง `AUTO_SEARCH_ARC`
  ล้อทั้งสองเป็นบวกตลอดการค้นหา ไม่หมุนอยู่กับที่เพื่อหาเป้าหมาย
- IR เจอให้ `AUTO_IR_ATTACK` เล็ง/ดันเต็ม 255 แม้กล้องไม่เห็นหรือแพ็กเก็ตจากคอมขาด
- IR จับด้านหน้าได้แล้วดันต่อเต็มกำลัง ไม่บังคับถอยทุก 2 วินาที
  ให้ภาพยืนยันการติดค้างและโอกาสดันตกก่อนเปลี่ยนมุม; พื้นขาวยังหลบตาม state เดิม
- เซนเซอร์พื้นขาวแทรกได้ทุก state: ถอยจนพ้นแล้วหันกลับ จากนั้นเดินหา/เข้าชนต่อเอง
- กล้องหลุดจะลองเปิดกล้องใหม่เอง Wi-Fi จะค้นหา IP และรับช่วง session เดิมกลับเอง
- พบสองแท็กครบอีกครั้งกลับสู่แผนภาพ ไม่ต้อง Start ใหม่; ID ซ้ำใช้ state บนหุ่นจนแยกแยะได้
- แถวสถานะระบุ ID ที่กล้องอ่านได้ และแยกว่าถูกใช้แล้ว ไม่พบ หรือพักเพราะตำแหน่งกระโดด
  เก็บประวัติผ่านเฟรมที่หลุดและยืนยันตำแหน่งที่กระโดดด้วยภาพต่อเนื่องก่อนรับกลับ

## การหยุดและเซนเซอร์บน ESP32

- ไม่ได้รับ DRIVE ใหม่ภายใน TTL (**350 ms**): กลับไป AUTO บน ESP32 โดยไม่ยกเลิก ARM
- STOP รับได้ทั้ง USB และ UDP โดยไม่ต้อง ARM และทำให้ challenge เดิมใช้ไม่ได้
- DRIVE ต้องตรง session, มาจากผู้ควบคุมที่ ARM และมี sequence เพิ่มขึ้น ปฏิเสธแพ็กเก็ตซ้ำ/ย้อนลำดับ
- เซนเซอร์พื้นด้านหน้ามีสิทธิ์เหนือคำสั่งกล้อง: ขาว → ถอยอย่างน้อย 120 ms ที่ 255 → เมื่อดำทั้งคู่ให้หมุน 130 ms ที่ 255
  ถ้ายังขาวจนถึง 550 ms ให้หันกลับแล้วตรวจพื้นซ้ำ ไม่หยุดค้างด้วย `EDGE_TIMEOUT`
- Stop ยังสั่งหยุดได้ระหว่างถอยหรือหมุนหลบขอบ และ IR จะไม่ทำให้เริ่มใหม่หลัง Stop
- หน้าจอแยก **PWM ที่สั่ง** ออกจาก **PWM จริงที่ ESP32 รายงาน** เพื่อเห็นเมื่อเซนเซอร์ขอบแทรกแซง

TTL เป็นอายุคำสั่งภาพก่อนเปลี่ยนไปใช้ state บนหุ่น ไม่ใช่เวลาตัด AUTO
เวลาหยุดจากปุ่ม Stop ยังรวมความหน่วงสื่อสารและแรงเฉื่อย เซนเซอร์พื้นเดิมมีด้านหน้าสองตัว
EN/รีเซ็ตถือเป็นการหยุดจริง แอปจะไม่ ARM กลับเองหลังรีเซ็ต แต่การหลุดของภาพ/Wi-Fi รับช่วงคืนได้เอง

## โปรโตคอลข้อความ v4 (STA_V6_AUTO)

หนึ่งบรรทัดต่อ UDP datagram ผ่าน Wi-Fi:

```text
PC -> PING <probe>
ESP -> PONG <probe> 4 <uptimeMs> <armed> <irBits> <whiteL> <whiteR> <action> <actualLeft> <actualRight>
PC -> HELLO <session>
ESP -> READY <session> <challenge> 4
ESP -> RESUMED <session> <lastSequence> 4  (HELLO เดิมขณะ AUTO ยังทำงาน)
PC -> ARM <session> <challenge>
ESP -> ARMED <session>
PC -> DRIVE <session> <sequence> <left:-255..255> <right:-255..255> <ttl:80..350> <assist:0..2> <motorCap:1..255>
PC -> STOP
ESP -> TEL <session> <sequence> <armed> <action> <actualLeft> <actualRight> <whiteL> <whiteR> <irBits> <uptimeMs>
```

`assist=0` ให้กล้องกำหนดล้อ/ถอย, `1` ให้ IR เสริมเข้าชน, `2` ใช้ state บนหุ่นเต็มรูปแบบ แม้ส่งล้อ 0/0
คำสั่งเก่าหมดอายุหรือ Wi-Fi หลุดเข้าสู่ state บนหุ่นโดยอัตโนมัติ คำสั่งภาพใหม่รับช่วงคืนทันที
เฟิร์มแวร์ยังรับ DRIVE แบบเดิม 6 ช่องได้; แอปใหม่ต้องการ STA_V6_AUTO ก่อน Start
PONG รายงานเซนเซอร์ก่อน Start เพื่อเช็ก IR โดยมอเตอร์ยังหยุด

`session` เป็นเลขสุ่มใหม่ทุกครั้งที่ Start; challenge ออกโดย ESP32
Stop เปลี่ยน challenge จึงใช้ ARM เก่ามาเริ่มใหม่ไม่ได้; การขาดคำสั่งไม่ใช่ Stop
Serial Monitor ส่ง `s` ตัวเล็กเพื่อหยุดทันทีได้ ส่วน `g` ของโปรแกรมเดิมไม่ได้ใช้แล้ว
